# 流程策略 — OpenPawz

> 关于流程可视化管道功能的内部路线图。
> 介绍 **指挥家协议 **(The Conductor Protocol)，作为 OpenPawz 发明三部曲中的第三人——与图书管理员方法(The Librarian Method)和工头协议(The Foreman Protocol)。

---

### OpenPawz 三部曲

| 协议 | 回答的问题 | 创新 |
|----------|-------------------|------------|
| **图书管理员方法** | *哪些* 工具可用于此意图？ | 通过嵌入实现意图驱动的发现 |
| **工头协议** | *如何* 以低成本执行动作？ | 通过自描述的 MCP 进行工人模型委托 |
| **指挥家协议** | *最优的方式* 执行此蓝图是什么? | AI 编译流执行，带有合并、提取、并行化、汇聚 |

它们共同组成: 图书管理员发现工具, 指挥家编译执行策略, 工头执行确定性操作——实现 AI 编排的工作流，支持超过 25,000 个集成，在现有平台无法匹配的速度和成本上运行。

---

## 指挥家协议

**意图编译流执行通过蓝图解释**

*OpenPawz 第三个创新。开源 (MIT)。*

### 问题

每一个工作流平台——Zapier、n8n、Make、Temporal、Airflow、Prefect——将一个流图看作源代码：遍历节点的顺序程序。每个节点是一个离散函数调用。数据通过字符串管道穿过边缘。这种模式是为了预 AI 时代的确定性 API 到 API 自动化设计。

Pawz 节点不是 API 调用——它们是 AI 代理。告知智能体“研究这个主题，起草一封邮件，审查草稿”可以在一个回合完成所有三件事。将该操作拆分为三个独立的 LLM 调用，并在这三者之间字符串管道传递:

1. **浪费时间** — 3 次 LLM 请求而不是 1 次
2. **破坏上下文** — 每一个节点从头开始，重新阅读上游内容作为纯文本
3. **失去主线** — 没有任何节点知道工作流的更广泛目标

这就像聘请一位优秀的作家并说：“第一步：研究。停下，把笔记给我。第二步：这里有一些别人写的笔记，草拟一封邮件。停下。” 每个步骤都会失去连贯性。

### 发明

指挥家协议将流图视为 **意图的蓝图**，而不是字面上执行的程序。在执行之前，指挥家会阅读整个蓝图并 **编译优化后的执行策略**。

```
传统方式：图表 → 顺序遍历 → 节点 → 节点 → 节点 → 节点 → 节点
指挥家：图表 → AI 编译器 → 优化策略 → 批量执行
```

指挥家执行四个转换：

#### 1. 合并

形成一致任务的相邻智能体节点合并为单个 LLM 调用。

```
之前：[研究] → [起草邮件] → [复查草稿]
之后：[研究、起草和复查一并进行]

3 次 LLM 请求 → 1 次。质量不变。上下文完整保留。
```

规则：相同的智能体档案、相同的模型、它们之间没有任何条件/分支、链条中没有副作用动作节点。保守起见，默认合并 3 个节点为 1 就是一个 3x 的速度提升。

#### 2. 提取

确定性动作从创意/推理工作中分离出来，并直接路由到工头处零 LLM 执行。

```
之前：[智能体: "发送邮件给john@..."] → engineChatSend → LLM思考 → MCP调用
之后:  [直接MCP调用通过工头] → 不涉及LLM

5 秒 → 200ms。AI在上游组成内容；行动只是发送内容。
```

节点种类决定路由：`tool`/`code`/`output`/`http` → 直接执行。
`agent`/`data` → LLM调用。`condition` → 结构化评估首先进行，语义条件回落由 AI 处理。

#### 3. 并行化

独立分支被识别为并发工作并同时执行。

```
之前: [抓取 GitHub 提交] → 等待 → [检查 Slack] → 等待 → [查询DB]
之后: [抓取 GitHub 提交 ‖ 检查 Slack ‖ 查询DB] → 同时进行

15秒 → 5秒。三个独立动作，在一个时钟周期完成。
```

检测是确定性的图分析：在相同深度且具有无共享边和无数据依赖的节点 → `Promise.all`。

#### 4. 汇聚 (汇聚网)

循环子图——所有其他工作流平台都不可能实现——以迭代共享上下文的空间处理，智能体在此处对话直到输出稳定。

```
之前: 智能体 A ↔ 智能体 B → 崩溃 (拓扑排序失败循环)
之后:  汇聚网:
  轮次 1: A 声明立场, B 响应
  轮次 2: A 反驳, B 反驳
  轮次 3: 输出稳定 → 收敛 → 停止
  → 综合器读取全部历史 → 最终输出
```

这是 n8n *实际上不能做的*。其执行模型要求有向无环图。循环是错误。在 Pawz 中，循环是对话。

最大迭代次数：5 (可配置)。收敛检测：比较连续输出。超时合成。

## 速度对比：Pawz 指挥家 vs n8n vs 当前 Pawz

### 方法

基于测量组件延迟估算的时间：
- LLM API 调用 (云端，流式)：2–8 秒，视复杂程度而定
- LLM API 调用 (本地 Ollama 7B)：1–4 秒
- 通过工头的 MCP 工具调用 (直接)：100–500 毫秒
- Tauri IPC 往返：~5毫秒
- HTTP API 调用 (外部服务)：100–800毫秒
- 指挥家编译 (读取蓝图的单次 LLM 调用)：1–3秒
- 轮询开销 (当前每个节点的执行器)：250毫秒–1秒
- 会话设置/拆除开支 (当前每个节点的执行器)：~200毫秒

### 情况 1：简单线性流 (5 个节点)

**触发 → 智能体 (研究) → 智能体 (草拟) → 工具 (发送电邮) → 输出**

| 平台 | 调用次数 | 实际耗时 | 原因 |
|------|---------|---------|------|
| **n8n** | 4 次 API 调用 | ~2秒 | 直接 API 调用，无 AI，确定 |
| **当前 Pawz** | 5 次 LLM 调用 (顺序) | **20–45秒** | 每个节点 = LLM 请求 + 轮询 + 会话开销 |
| **Pawz + 指挥家** | 1 次 LLM 调用 + 1 次 MCP 调用 | **4–9秒** | 节点 2+3 合并, 节点 4 提取, 输出直通处理 |

**加速比：比当前 Pawz 快 4–5 倍。与 n8n 在 AI 工作的性能方面相当，
加上 n8n 无法提供的 AI 功能。**

### 情况 2：并行扇出 (8 个节点)

**触发 → [GitHub 提交 ‖ Slack 消息 ‖ Jira 工单] → 智能体 (摘要) → 发送报告 → 输出**

| 平台 | 调用次数 | 实际耗时 | 原因 |
|------|---------|---------|------|
| **n8n** | 5 次 API 调用 | ~3秒 | 并行 API 调用 + 顺序合并/发送 |
| **当前 Pawz** | 8 次 LLM 调用 (顺序) | **35–70秒** | 每个节点等待前一个，即使分支独立 |
| **Pawz + 指挥家** | 3 次 MCP 调用 (并行) + 1 次 LLM 调用 + 1 次 MCP 调用 | **5–10秒** | 3 次提取 + 并行化，总结 = 1 次 LLM，发送 = 直接 MCP |

**加速比：比当前 Pawz 快 5–7 倍。**

### 情况 3：复杂的双向辩论流 (6 个节点)

**触发 → 智能体 A ↔ 智能体 B (3 轮) → 合成器 → 输出**

| 平台 | 调用次数 | 实际耗时 | 原因 |
|------|---------|---------|------|
| **n8n** | ❌ 不可能 | N/A | 无法执行循环。图形验证错误。 |
| **当前 Pawz** | ❌ 损坏 | N/A | 拓扑排序失败，随机追加节点 |
| **Pawz + 指挥家** | 1 网格 (3 轮 × 2 智能体) + 1 次 LLM 调用 | **15–25秒** | 收敛网格处理循环，综合器合并成 1 次调用 |

**加速比: ∞ — 当前 Pawz 或 n8n 都无法实现此流程类型。**

### 情况 4：大型生产流 (20 个节点)

**Webhook → 4 个并行数据获取 → 条件分支 → 3 个智能链 (×2 分支) → 4 个动作 → 错误处理 → 输出**

| 平台 | 调用次数 | 实际耗时 | 原因 |
|------|---------|---------|------|
| **n8n** | 16 次 API 调用 | ~8秒 | 尽可能并行，全部确定 |
| **当前 Pawz** | 20 次 LLM 调用 (顺序) | **80–160秒** | 每个节点顺序，每一次操作经过 LLM |
| **Pawz + 指挥家** | 编译 (1) + 4 MCP 并行 + 2 LLM (已合并链) + 4 MCP 并行 + 1 直通 | **8–18秒** | 6 个代理节点 → 2 个已合并的 LLM 调用；8 个动作节点 → 直接 MCP；4 个获取并行 |

**加速比：比当前 Pawz 快 8–10 倍。在 2 倍范围内达到纯 n8n 的速度，加上 AI。**

### 总结

| 情况 | 当前 Pawz | Pawz + 指挥家 | n8n | 指挥家 vs 当前 |
|------|-----------|---------------|-----|---------------|
| 5 节点线性 | 20–45秒 | 4–9秒 | ~2秒 | **4–5 倍更快** |
| 8 节点扇出 | 35–70秒 | 5–10秒 | ~3秒 | **5–7 倍更快** |
| 6 节点双向 | 损坏 | 15–25秒 | 不可能 | **∞ (启用新能力)** |
| 20 节点生产 | 80–160秒 | 8–18秒 | ~8秒 | **8–10 倍更快** |

模式：流越大、越复杂，指挥家的优势就越大——因为有更多的机会可以合并、提取和并行。简单的 2 节点流几乎没有收益（并且完全跳过指挥家通过自适应阈值）。

### 为什么 Pawz 无法匹配纯 n8n 速度（及为何不必需要）

n8n 节点是直接的 API 调用 — 100-500 毫秒每次。 没有 AI 推理。
Pawz 智能体节点涉及 LLM 推断 — 每次为 2-8 秒。那是智能的固有成本。
指挥家最小化 LLM 调用的 *数量*，但每次
调用仍然需数秒。

价值主张并不是 "比 n8n 的确定性任务更快。" 它是:
**"对于需要 AI 推理的任务尽可能快，确定性
任务的执行速度与 n8n。"**

## 性能瓶颈分析 (当前执行器)

### P0 — 每个节点 = 完整的 LLM 请求循环

Agent/tool/data/condition 节点全部调用 `engineChatSend()` → Tauri IPC → Rust →
LLM 提供商 → 流返回。甚至确定性操作如 "发送邮件" 通过 AI 代理路由。5 个节点
的流 = 5 次顺序的 LLM 调用，每一个需要消耗 2–10s。

**指挥家修复方法：** 提取 + 合并。通过工头绕过 LLM 进行确定性操作。
相邻代理节点合并成单个 LLM 调用。

### P1 — 顺序执行

`for (let i = 0; i < plan.length; i++)` 遍历一个个节点。可以
并行的独立分支反而顺序等待。

**指挥家修复方法：** 并行化。独立分支通过图形分析检测到
并且并发执行。

### P2 — 轮询基础流处理

在 `engineChatSend()` 之后，执行器每 250 毫秒轮询检查流是否结束，
加上用于同步响应的一秒钟回退超时。增加了每节点的 250ms–1s 的
人为延时。

**修复方法：** 替换轮询为事件驱动完成。解析来自 `subscribeSession` 的承诺
当流结束时回调。

### P3— 全 SVG 毁灭重建

`renderGraph()` 清除所有 SVG 组并从头创建所有元素。
在每个拖动帧上调用。以 20 节点 + 25 边为例 =
200 个在每次鼠标移动事件被销毁/再创建的 SVG 元素。

**修复方法：** `requestAnimationFrame` 拖动过程中限制。受影响区域渲染。
节点 ID → O(1) 更新的 SVG 元素映射。

### P4 — O(n) 线性扫描

节点查找使用 `graph.nodes.find()` 无处不在。在 60fps
拖拽期间每次多个查找每秒千次。

**修复方法：** `Map<string, FlowNode>` 索引。O(1) 查询。

### P5 — 双向流破环 DAG 执行

Kahn’s 拓扑排序假设 DAG。双向边创建循环。代码以任意顺序附加
剩余节点。

**指挥家修复方法：** 收敛网格。循环子图运行直到输出稳定。

## 实施阶段

### 第 0 阶段 — 快速收益（无需指挥家）

> **目标：** 通过工程修复立即提高速度。
> **精力：** 少。**影响：** 明显。

#### 0.1 事件驱动流完成

- 为 `subscribeSession` 添加 `onComplete` 回调
- 在回调中从执行器解析承诺替换 250ms 轮询
- 删除 1 秒回调的 setTimeout
- 节省 250ms–1ms/节点 (免费提速)

#### 0.2 画布性能

- `requestAnimationFrame` 对 `renderGraph()` 拖动中限制
- 构建 `Map<string, FlowNode>` 和 `Map<string, FlowEdge>` 指标
- 受影响区域呈现：追踪更改的节点 ID, 仅重建那些 SVG 元素
- 视口遮挡：不呈现可见区域外的节点

#### 0.3 节点索引地图

- 替换所有 `graph.nodes.find(n => n.id === id)` 为 `nodeMap.get(id)`
- 替换所有 `graph.edges.filter(e => e.from === id)` 为邻接列表
- 图加载时构建图，增量更新

### 第 1 阶段 — 基础

> **目标：** 稳定性，持久性和最低预期功能。
> **精力：** 中。**影响：** 高。

#### 1.1 Rust 后端持久性

- 添加 Tauri 命令：`engine_flows_save` , `engine_flows_load`,
  `engine_flows_list`, `engine_flows_delete`
- 在 SQLite 跟踪器及代理/会话中存储流
- 首次启动时从 localStorage 迁移
- 图形更改自动保存 (节流 1 秒)
- 保留 localStorage 作为离线备用

#### 1.2 后端调度

- 将计划刻度移到 Rust 侧线程
- 流运行当应用打开时，不仅在选项卡聚焦时
- 数据库中持续计划注册表
- 带有运行历史记录的火灾日志

#### 1.3 撤销/重做

- 命令堆栈模式：对每个突变推送图快照
- Ctrl+Z / Ctrl+Shift+Z 密钥绑定
- 限制堆栈到 ~50 个条目
- 工具栏的视撤销/重做按钮

#### 1.4 导入 / 导出

- 导出: 工具栏按钮 → `serializeGraph()` → 下载为 `.pawflow.json`
- 导入: 工具栏按钮 → 文件选择器 → `deserializeGraph()` → 添加到列表
- 使用用户友好的错误导入时验证架构

#### 1.5 执行历史

- 每次运行的 `FlowExecEvent[]` 保留在数据库中
- 在侧边栏中添加“运行”选项卡，含状态，持续时间，时间戳
- 点击一个运行以查看每个节点的结果
- 在每个历史条目上重新运行按钮

### 第 2 阶段 — 指挥家协议

> **目标：** 实现 AI 编译流执行。
> **努力：** 大。**影响：** 转变性。

每个步骤独立发布。每个步骤使流速度更快。完整的指挥家是这些部分的总和。

#### 2.1 提取（确定性操作绕过）

最简单的指挥家原语。不需要 AI 编译—纯静态
分析。

- 新的 `http` 节点类型：方法、URL、标题、正文、响应映射
- 新的 `mcp-tool` 节点类型：直接 MCP 工具调用，无需代理
- 这些节点完全绕过 `engineChatSend()` — 直接 Tauri IPC 到 Rust
  生成 HTTP/MCP 调用并返回结构化数据
- 为空（仅操作提示）的现有 `(tool)` 节点路由通过工头
- 预期改进：2–8 秒 → 200 毫秒 每个确定性节点

#### 2.2 平行化（并发分支执行）

确定性图分析—不需要AI。

- 在 `buildExecutionPlan()` 中，按深度级别分组节点
- 在同一深度且没有相互数据依赖的节点 → `Promise.all`
- 通过单独事件流报告并行进度
- 可视指示器：并行节点同时激活

#### 2.3 折叠（代理节点合并）

首个AI辅助原语。保守启发式，暂时还不需要指挥家代理。

- 检测连续代理节点链：
  - 相同的代理配置文件或未知配置
  - 相同的模型或未知模型替代
  - 连接它们之间的条件/分支节点
  - 链中没有副作用的操作节点
- 将它们的提示合并成一个复合提示：
  `"步骤 1: {node1.prompt}\n步骤 2: {node2.prompt}\n步骤 3: {node3.prompt}"`
- 执行成一个 LLM 调用，解析结构化输出回到各个节点状态
- 可配置：用户可在配置中将节点标记为 "不要合并"
- 预期改进：N 个相邻代理节点 → 1 个 LLM 调用

#### 2.4 收敛（循环的收敛网格）

新颖原语。使得其他平台不可能的流程类型成为可能。

- 通过执行计划期间的 DFS 检测图中的循环
- 对非循环子图: 标准拓扑执行
- 循环子图的：创建收敛网格
  - 所有循环内代理可见的共享上下文空间
  - 迭代轮次：每个代理都能看到所有以前的输出
  - 收敛检测: 连续轮次间的余弦相似度（使用相同的嵌入基础架构
如同图书管理员）
  - 硬上限：5轮次（每个网格可配置）
  - 收敛或上限：强制合成步骤
- 视觉效果：网格节点在共享边界框内以及轮次计数器显示

#### 2.5 Full Conductor Agent

顶点。一个AI代理阅读完整的流蓝图并使用四种基元生成
编译策略。

- Conductor 在执行开始前作为单个LLM调用运行
- 输入：序列化的 FlowGraph JSON + 可用的代理配置文件 + 节点配置
- 输出：ExecutionStrategy JSON（阶段，单元，合并组，网格配置）
- 策略验证：每个节点恰好出现一次，依赖关系得到遵守，
确定性节点正确分类
- 验证失败: 落回顺序执行器（安全路径）
- 自适应阈值: 仅调用含有4+节点的 flows，或
分支，或任何循环。低于该阈值，直接运行顺序执行器。
- Conductor 开销: 1–3s (跨节约数小时的5–50s的摊销)

**Conductor 提示规范:**

```
您是用于AI工作流执行引擎的 Conductor。您将收到
描述AI代理节点管道、工具节点、代码
节点及操作节点的流图（JSON）。

您的工作是使用这些基元编译优化的执行策略：
- 合并：将相邻代理节点合并到单个 LLM 调用中
- 提取：将确定性节点（工具，代码，HTTP）路由到直接执行
- 并行化：并发运行独立分支
- 收敛：将循环子图作为迭代网格处理

输出阶段，单元和配置的 JSON ExecutionStrategy。
不执行任何事情。只生成计划。
```

## 架構注意事項

### Conductor + Foreman + Librarian 流程

在 Conductor Protocol 下執行時：
```
1. 按下 "運行" （或計劃觸發）
2. CONDUCTOR 解讀 FlowGraph JSON
3. → 識別智能體鏈 → 標記 COLLAPSE
4. → 識別工具/代碼/HTTP 節點 → 標記 EXTRACT
5. → 識別獨立分支 → 標記 PARALLELIZE
6. → 識別循環 → 標記 CONVERGE （網格）
7. → 生成 ExecutionStrategy JSON
8. 驗證器檢查策略針對圖（每個節點，依賴關係）
9. → 如果無效：退回連續執行器
10. 執行器遍歷策略階段：
11. → 合併智能體單位：每個單位 1 個 LLM 調用
12. → 提取動作單位：LIBRARIAN 發現工具 → 通過 MCP 由 FOREMAN 執行
13. → 並行單位：Promise.all
14. → 網格單位：迭代輪次 → 收斂檢測 → 合成
15. 結果回流；失敗時的運行器重新編譯
```

### n8n 橋接集成

Rust 後端已具有 n8n API 集成（`engine_n8n_list_workflows`，
`engine_n8n_trigger_workflow`，`engine_n8n_deploy_mcp_workflow`）。

**機會：** 增加一個 "n8n 工作流" 節點類型，該節點觸發 n8n 工作流
捕獲輸出。指揮家將這些提取為直接動作用途。
即時，600+ n8n 集成可通過 Pawz 流程使用，在原生速度上執行，
並由 AI 智能體協調。

### 自適應指揮家閾值

指導員本身花費 1–3s（一個 LLM 調用以編譯策略）。對於
微不足道的圖，這個開銷超過節省。

**規則：** 只有當圖形證明有必要時才調用指揮家：
- 4+ 節點，或者
- 任何分支（擴展/收縮），或者
- 任何循環（雙向邊），或者
- 混合節點類型（智能體+動作）

低於閾值：直接運行連續執行器。指揮家是
附加的，從不強制。

### 測試覆蓋

三個測試文件涵蓋原子，執行器-原子和解析器 (~620 行線)。
每一個新的指導原語都需要自己的測試套件：
- `conductor.test.ts` — 策略編譯，合併檢測，提取
  分類，並行分組，網格檢測
- `conductor-exec.test.ts` — 策略執行，階段排序，備用方案
- `convergent-mesh.test.ts` — 迭代、收斂檢測、強制合成
