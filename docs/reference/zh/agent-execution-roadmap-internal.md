## 执行摘要

OpenPawz 已经拥有了其他桌面 AI 平台所没有的东西：**编排者协议**（AI 编译流执行）、**领班协议**（通过工作模型实现免费工具执行）、**工具 RAG**（语义工具发现）和**项目记忆**（生物启发的记忆）。这些都是真实、已实现、已测试的系统——不是白皮书。

但现在，我们的智能体仍然通过**自然语言**进行通信。当智能体A委托给智能体B时，它会写英语。当一个智能体调用一个工具时，它生成 JSON 文本，序列化，通过 IPC 发送，引擎解析，调用 API，将结果再次序列化为 JSON，智能体读取。每个步骤都是翻译层。每次翻译都意味着延迟和信息丢失。

此路线图描述了我们如何消除这些翻译层——**不是发明新物理定律，而是消除行业中被接受为正常的浪费。**

核心洞察：智能体执行中的瓶颈不是模型思考的速度。而是我们让它们思考多少次。每次不必要的推理调用花费2-10秒。每次不必要的 JSON 序列化都会浪费 CPU。每当我们将400个工具模式塞入上下文时，我们就消耗了数千个令牌，而模型必须先读完它们才能行动。

**我们已经解决了其中的部分问题。** 编排者的-collapse-原语将3个LLM调用合并为1个。提取功能对于确定性节点完全绕过LLM。工具RAG只加载智能体需要的工具。领班将机械工作委托给便宜模型。这个路线图是沿着同一轨迹的下一步。

## 为什么我们要这样做

### 我们要解决的问题

今天每一个AI智能体平台——包括我们自己——都遵循相同的循环：

```
用户说话 → 模型读取所有内容 → 模型思考 → 模型输出文本 →
引擎解析文本 → 引擎调用API → API返回数据 →
引擎序列化结果 → 模型读取结果 → 模型再次思考 → ...重复
```

每次循环需要2-10秒（LLM推理）加上网络延迟。5步任务需要20-50秒。用户会注意到。用户会离开。

### 这会改变什么

| 指标 | 当前 | 第四阶段后 |
|--------|-------|---------------|
| **每项任务平均工具调用次数** | 3-5个顺序调用 | 1个规划调用 + 并行执行 |
| **工具选择开销** | 每次请求约5,000个token的框架 | 约800个token（工具 RAG，已完成） |
| **JSON解析失败率** | 约5%的工具调用需要重试 | 0%（受约束解码） |
| **内部 IPC 格式** | JSON文本（人类可读） | 二进制（机器优化） |
| **多步任务延迟** | 20–50s | 4–12s |
| **每项任务的Token成本** | 100%基准 | 基准的约40% |

### 为什么其他人没有这样做

1. **向量不兼容性** — 每个模型都有自己的内部表示。没有通用的"思维格式"。该行业使用英语作为最低公分母，因为它适用于任何地方。我们不需要解决这个问题——我们需要围绕它进行优化。

2. **安全可读性** — 监管机构和用户希望阅读人工智能正在做的事情。二进制协议让人害怕。我们的答案：领班已经在API调用级别监控，而不是语言级别。OAuth作用域从物理上防止过度扩展，无论代理"说"什么。

3. **传统基础设施** — 互联网运行在REST和JSON之上。Gmail不会暴露"潜在向量接口"。Slack不会接受张量嵌入而不是文本。我们必须去满足外部系统的现状。但在内部——我们自己的引擎组件之间——我们可以控制线的两端。

4. **这需要正确的基础。** 你需要编排者（流编译）、领班（费用等级分离）和工具RAG（动态工具加载）才能使这一切有意义。我们具备所有三个要素。这就是为什么我们能做到而其他人不能——他们首先要搭建基础。

## 计划

### 第0阶段：Action DAG 规划 (单次执行计划)

**风险：**低——附加功能，无破坏性变化
**依赖项：**无(基于现有编导器构建)

#### 是什么

目前，当智能体有多步任务时，它以循环方式逐个执行工具：

```
第一步: 智能体思考 → 调用工具A → 等待结果
第二步: 智能体读取结果 → 思考 → 调用工具B → 等待
第三步: 智能体读取结果 → 思考 → 调用工具C → 等待
总计: 3次推理调用，3次顺序工具执行
```

Action DAG 规划会要求模型在一个推理调用中输出**完整的执行计划**：

```
第一轮：代理思考 → 输出计划：
  {
    "nodes": [
      { "id": "a", "tool": "google_calendar_list", "args": {...} },
      { "id": "b", "tool": "gmail_search", "args": {...} },
      { "id": "c", "tool": "gmail_send", "args": {...}, "depends_on": ["a", "b"] }
    ]
  }

引擎：并行执行 A 和 B → 将结果传递给 C → 执行 C
总计：1 个推理调用，2 次往返（并行 + 串行）
```

#### 为什么重要

这是我们可以做出的**影响最大的单一优化**。任何智能体任务的主要成本不是工具执行——而是每轮推理的 2-10 秒 LLM 时间。将 5 轮减少到 1-2 轮，可以将任务延迟降低 60-80%。

编排器已经为*流程*（预设工作流）做到了这一点。Action DAG 将其延伸到*对话* —— 代理本身将成为一个小编译器，输出执行计划而不是做顺序决策。

#### 如何构建

1. **新的系统提示部分** — 指示模型，对于多步骤任务，它可以输出一个包含动作 DAG 的 `plan` 工具调用，而不是分别调用工具。

2. **Rust 中的计划解析器** — 新模块 `engine/plan/` 包含：
   - 验证 DAG（无循环，所有依赖项存在，所有工具有效）
   - 使用与编排器相同的深度分组算法来计算执行阶段
   - 通过 `tokio::join!` 执行并行操作

3. **回退机制** — 如果模型没有输出计划（或输出格式错误），现有的顺序工具调用循环会继续不变。该计划始终是附加的。

4. **结果注入** — 并行执行之后，所有结果都注入上下文中，以便进行单个后续推理调用，在该调用中代理合成答案。

#### 并行执行故障转移

当执行计划 DAG 时，单个节点可能会失败——API 超时、令牌过期、工具返回错误。系统绝不能因为在一分支失败就放弃整个计划。故障转移策略：

1. **节点错误隔离** — DAG 中的每个节点在其自身的 `tokio::spawn` 内执行，带有 `catch_unwind` 边界。节点 B 中的恐慌或错误不会导致节点 A 的并行执行崩溃。失败的节点会生成结构化错误结果：`{ "status": "error", "node_id": "b", "error": "401 Unauthorized", "retryable": true }`。

2. **退避重试** — 如果节点失败且错误可重试（网络超时、429 限速、5xx 服务器错误），执行器最多尝试 2 次，使用指数退避（1 秒、3 秒）。不可重试的错误（401、403、404、模式验证）立即失败。

3. **依赖感知降级** — 如果节点 B 失败且节点 C 依赖于 B，执行器不会尝试 C。相反，C 接收一个合成结果：`{ "status": "skipped", "reason": "dependency 'b' failed" }`。独立节点（不依赖 B）继续不受影响地执行。

4. **部分结果合成** — 最终的合成推理调用接收所有结果——成功、错误和跳过。模型可以告诉用户："我创建了日历事件并发送了邀请，但是因为 Gmail 返回了令牌错误而无法搜索您的电子邮件。您希望我重新尝试那部分吗？"

5. **自动计划分割** — 如果整个并行阶段失败（例如，网络断开），执行器将对剩余节点回落到顺序模式。这重用现有智能体循环——计划优雅降级而不完全失败。

6. **按节点超时** — 每个节点都有可配置的超时（默认值：API 调用 30 秒，MCP 工具调用 60 秒）。超时时，该节点被视为可重试的失败。整个计划有一个硬性超时 5 分钟，结束后取消所有正在进行的节点并将部分结果进行合成。

```
计划：A ‖ B ‖ C → D（依赖于 A、B、C）

场景：B 失败，出现500错误
  - A: ✅ 成功
  - B: ❌ 重试 1 (1s) → ❌ 重试 2 (3s) → ❌ 最终失败
  - C: ✅ 成功
  - D: 使用A + C 结果 + B 错误上下文执行
  - 用户看到: "完成3个步骤中的3个。步骤B（Gmail 搜索）失败——服务器错误。"
```

#### 影响

| 之前 | 之后 |
|--------|-------|
| 5 步任务需要 5 次调用 | 1-2 次调用 |
| 20-50 秒延迟 | 4-12 秒延迟 |
| 顺序工具执行 | 尽可能并行 |
| 约 15,000 个令牌被消耗 | 约 5,000 个令牌被消耗 |

#### 受影响的文件
- `src-tauri/src/engine/plan/` — 新模块（解析器、验证器、执行器）
- `src-tauri/src/engine/agent_loop/mod.rs` — 检测计划工具调用，移交给计划执行器
- `src-tauri/src/engine/chat.rs` — 为支持模型添加计划工具到系统提示
- `src-tauri/src/engine/tools/mod.rs` — 注册计划伪工具

### 第一阶段：受约束解码（零解析失败）

**风险：** 低-中等 — 需要特定提供商集成
**依赖项：** 无（独立于第0阶段）

#### 是什么

如今，当模型调用一个工具时，它会自由生成JSON。有时会产生：
- 字符串期望对象（我们刚刚修复了 `google_api` 问题）
- 必需字段缺失
- 工具不理解的额外字段
- 格式错误的JSON，无法完全解析

受约束解码迫使模型仅生成生产有效输出的标记。模型字面上*无法*生成格式错误的工具调用，因为标记样本器只允许在每个位置匹配工具JSON架构的标记。

#### 为什么重要

解析失败会引发重试循环。每次重试又是另一个完整的推理调用（2-10s，全部标记成本）。我们当前的重试率约为5%——虽然不算灾难性，但放大后这意味着20次工具调用中就有1次浪费了完整来回。对于每会话运行数十次工具调用的高级用户来说，这累积起来很可观。

更重要的是，受限解码是"超越语言交流"的**实用版本。**我们不跳过语言——我们*限制*它只能生成有效表达。模型的输出空间从"任何字符串"缩小到"有效的工具调用JSON"，这是熵和错误表面的巨大收缩。

#### 如何构建

1. **OpenAI:** 已支持 `response_format: { type: "json_schema", json_schema: {...} }` 和函数调用中的 `strict: true`。我们只需要以正确格式传递我们的工具模式。结构化输出保证 100% 模式一致性。

2. **Anthropic:** 支持 `tool_choice: { type: "tool", name: "..." }` 来强制特定工具调用。尚未具有语法级强制力，但强制工具选择消除了"模型决定不调用任何东西"的失败模式。

3. **Google Gemini:** 支持 `response_mime_type: "application/json"` 与 `response_schema`。可通过函数声明结合用于结构化工具调用。

4. **本地模型 (Ollama):** Ollama 对所有模型支持 `format: "json"`，`llama.cpp` 后端支持 GBNF 语法进行完整方案约束。我们可以将工具方案作为语法传递。

5. **回退：** 对于不支持约束解码的供应商，我们保持当前解析与重试逻辑。这始终是附加的。

#### 影响

| 之前 | 之后 |
|--------|-------|
| ~5％解析失败率 | 支持的供应商为0％ |
| 重试循环每次消耗2–10秒 | 无需重试 |
| 防御性解析代码贯穿各处 | 干净确认有效的输入 |
| LLM可虚构字段名 | 仅限方案约定的字段名 |

#### 受影响的文件
- `src-tauri/src/engine/providers/openai.rs` — 在功能定义中添加 `strict: true`
- `src-tauri/src/engine/providers/anthropic.rs` — 添加 `tool_choice` 模式
- `src-tauri/src/engine/providers/google.rs` — 添加 `response_schema` 支持
- `src-tauri/src/engine/tools/mod.rs` — 用于Ollama的方案转语法转换
- `src-tauri/src/engine/agent_loop/mod.rs` — 当激活约束解码时移除重试-解析-失败处理

### 第二阶段：嵌入索引工具注册表（扩展至100,000个工具）

**风险：** 低 - 扩展现有 Tool RAG
**依赖关系：** 构建在现有的 `tool_index.rs` 和 Engram 嵌入管道上

#### 是什么

工具 RAG 已经处理了"工具过多"问题，让智能体调用 `request_tools("send email")` 并只返回相关工具。但当前实现：

- 按需嵌入工具描述（首次调用建立索引）
- 在内存中存储嵌入（重启后丢失）
- 遍历所有工具搜索
- 不动态索引来自 n8n 的 MCP 工具

嵌入索引工具注册表使这变得持久、快速且完整：

1. **持久化向量存储** — 在 SQLite 中存储工具嵌入，重启后仍然存在
2. **增量索引** — 当发现新 MCP 工具或安装社区包时，只对新工具进行嵌入
3. **分层搜索** — 首先与工具*类别*（17 个领域）匹配，然后在匹配的领域内搜索。两阶段检索。
4. **MCP 自动索引** — 每次 `mcp_refresh` 发现新工具时，它们会自动嵌入和索引

#### 为什么重要

今天，我们有大约 75 个内置工具 + 无论 MCP 从 n8n 暴露什么。随着我们发展达到数百个本地工具和数千个 MCP 工具，当前系统将无法扩展。在上下文中塞入 1000 个工具描述是不可能的（约 200,000 个令牌）。即使是第一次调用时嵌入所有工具也需要显著时间。

更重要的是，这是我们正确处理"AI 通过语言外方式通信"洞察的方式。代理不读英文工具描述并选择一个——它查询向量空间，在那里工具表示为嵌入，最近的匹配被返回。代理的意图与工具注册表之间的"通信"发生在嵌入空间中，而不是自然语言。这正是工具 RAG 的工作方式；我们是让它更快更持久。

#### 如何构建

1. **新的 SQLite 表** — `tool_embeddings` 列包括：`tool_name TEXT PRIMARY KEY, description TEXT, embedding BLOB, domain TEXT, source TEXT ('builtin'|'mcp'|'community'), updated_at INTEGER`

2. **启动时构建** — 更新后的首次启动时，在后台嵌入所有工具（非阻塞）。后续启动时，只嵌入更改的工具。

3. **层次检索:**
   ```
   查询: "book a meeting"
   步骤 1: 嵌入查询 → 余弦相似度对比 17 个领域质心 → 最优领域 = "google" (0.87)
   步骤 2: 在 "google" 领域内搜索 → [google_calendar_create (0.92), google_calendar_list (0.78)]
   步骤 3: 返回 top-k 工具
   ```

4. **MCP 钩子** — 在 `registry.rs` 中，`register_tools()` 之后触发背景嵌入新工具。

5. **去重** — 如果 MCP 工具与内置工具有重叠（例如，都可以发送 Slack 消息），则优先使用内置工具（更快，无 n8n 开销）。

#### 嵌入模型故障转移（未安装本地模型时）

工具 RAG 和这个注册表依赖于嵌入——工具描述的矢量表示。今天，嵌入由本地 Ollama 模型 (`nomic-embed-text`) 生成。但并非每个用户都会安装 Ollama，一些环境（锁定的企业机器、低配置硬件）根本无法运行本地模型。系统必须能够在没有本地嵌入模型的情况下运行。

故障转移链（每个层级转移到下一个）：

1. **第1层：本地 Ollama**（首选） — `nomic-embed-text` 通过 Ollama。每嵌入约 50ms，零成本，全隐私。这是 Ollama 运行时的默认设置。

2. **第2层：云端嵌入 API** — 如果 Ollama 不可用，使用用户配置的云供应商嵌入端点：
   - OpenAI: `text-embedding-3-small` （~$0.02 每 1M 个 tokens — 工具描述很小）
   - Google: `text-embedding-004` （免费套餐可用）
   - Anthropic: 当前无嵌入 API — 跳转到第3层
   - 供应商根据用户在设置中配置的 AI 供应商选择。如果他们使用 OpenAI 进行聊天，我们也使用 OpenAI 进行嵌入。无需额外配置。

3. **第3层：BM25 关键词搜索**（无嵌入） — 如果完全无可用的嵌入模型（无 Ollama、无云 API 密钥，或用户离线），工具库将退回到 **BM25 全文搜索** 工具名称和描述。这是 Engram 已使用的相同 BM25 引擎。它不如矢量搜索语义丰富（"book a meeting" 无法很好地匹配 "google_calendar_create"），但它仍可用于精确和部分关键词匹配。

4. **第4层：仅领域匹配**（绝对备选） — 如果连 BM25 都没产生结果，则退回到领域分类法。根据简单的关键词规则将 `request_tools` 查询分类到 17 个技能领域之一（例如，查询包含 "email" 或 "mail" → email 域）。返回该领域的所有工具。这始终有效——无需模型、无需索引，只是字符串匹配。

**检测和转换：**
- 启动时，引擎探测 Ollama 在 `http://127.0.0.1:11434/api/tags`。如果响应，激活第 1 层。
- 如果 Ollama 不在，引擎检查云 API 密钥。如果存在，激活第 2 层。
- 如果两者都不可用，自动激活第 3 层（BM25）。在 UI 中显示非阻塞警告："无嵌入模型可用 — 工具搜索使用关键词匹配。如需更好结果，请安装 Ollama 或配置云供应商。"
- 如果以后（用户在会话中间启动它）Ollama 变得可用，引擎在下一次 `request_tools` 调用中检测到这一点并提升回第 1 层，触发后台重新索引。

**缓存的嵌入在模型不可用时仍幸存：**
- 由第 1 层或第 2 层计算的嵌入存储在 SQLite 中。如果用户以前有 Ollama 现在却没有，缓存的嵌入仍可用于矢量搜索——只有*新*工具（来自 MCP 发现）将退回到 BM25。这意味着注册表优雅降级：现有工具保持矢量搜索质量，新发现工具使用关键词备用方案，直到再次可用嵌入模型。

#### 影响

| 之前 | 之后 |
|--------|-------|
| 内存索引，重新启动时重建 | 持久化 SQLite，启动瞬间可用 |
| 搜索遍历所有工具 | 分层：领域 → 工具 |
| MCP 工具未编制索引 | 发现时自动编制索引 |
| 约 75 个工具可搜索 | 100,000+ 工具可搜索 |
| 首次 `request_tools` 调用: ~2s（构建索引） | 首次调用: <100ms（预先构建） |

- `src-tauri/src/engine/tool_index.rs` — 持久化层，层次搜索，增量索引
- `src-tauri/src/engine/sessions/schema.rs` — 新的 `tool_embeddings` 表

### 第3阶段：内部通信的二进制IPC

**风险：** 中等 — 触及核心IPC边界
**依赖关系：** 第0阶段（计划执行器需要高效序列化）

#### 是什么

目前，引擎组件之间的每一次通信都使用JSON：
- 前端 ↔ Rust引擎：通过Tauri IPC的JSON
- 代理循环 ↔ 工具执行器：Rust结构（已经高效）
- 引擎 ↔ MCP服务器：JSON-RPC（协议要求）
- 引擎 ↔ AI提供商：通过HTTP的JSON（协议要求）

我们无法改变外部协议（Gmail和OpenAI都期望JSON）。但我们控制：
- **前端 ↔ 引擎IPC** — 目前是JSON。可以是二进制的。
- **工具调用序列化** — 当前是 `serde_json::Value`。可以是零拷贝二进制。
- **代理间消息** — 目前存储在SQLite中的文本。可以是结构化二进制。
- **计划DAG执行结果** — 第0阶段的并行结果可以是二进制。

#### 为什么重要

JSON解析不是单个工具调用的瓶颈。但对于高频操作——流式传输令牌、计划DAG中的快速工具序列、实时通道桥接消息——串行化 → 传输 → 反序列化的累积成本是显著的。每次JSON解析都是分配。每次序列化都是UTF-8编码过程。

像FlatBuffers（零拷贝读取）或MessagePack（紧凑、快速）这样的二进制格式消除了这些成本：
- **零拷贝** — 接收者直接读取字节，无需分配新对象
- **紧凑** — 比等效JSON小60-80% (没有键名，没有引号，没有空格)
- **类型安全** — 模式是在编译时的，而不是运行时解析的
- **快10-50倍** — 无需解析、无需UTF-8解码、无需转义处理

对于计划DAG执行器（第0阶段），这很重要：当5个工具结果并行返回并且需要组合成单个上下文注入时，二进制序列化避免了5个单独的解析-序列化周期。

#### 如何构建它

1. **Tauri IPC的MessagePack** — Tauri v2支持自定义序列化。将JSON替换为高频率事件的MessagePack（流式传输token，工具结果）。为了便于调试，在不常使用的命令（设置，代理CRUD）中保留JSON以便人类可读。

2. **计划结果的FlatBuffers** — 计划执行器（第0阶段）使用FlatBuffers将工具结果组装到单个缓冲区中。在注入到下一个推理上下文时进行零拷贝读取。

3. **代理间通信的Protobuf** — 当代理A委派给代理B（代理间消息传递）时，消息可以是结构化的Protobuf，而不是自由文本。双方代理的工具模式是预共享的，因此消息格式是已知的。

4. **首先进行基准测试** — 在提交给任何格式之前，我们在实际工作负载上进行基准测试。如果JSON对于某个路径（如设置CRUD）足够快，则我们保留JSON。仅在测量显示>5倍改进的地方进行交换。

#### 影响

内部可衡量（对用户来说除了延迟改善外不明显）：

| 路径 | 之前 | 之后 |
|------|--------|-------|
| SSE令牌流（高频率） | 每个令牌的JSON | MessagePack批次 |
| 工具结果组装（计划DAG） | 5× JSON解析 | 1× FlatBuffer读取 |
| 代理到代理的委托 | 英文文本 | Protobuf结构 |
| 前端事件总线 | JSON事件 | MessagePack事件 |

**预期在多工具任务上的延迟降低：15-30%**（在第0阶段由于较少推理调用而减少的60-80%基础上）。

#### 受影响的文件
- `src-tauri/src/engine/agent_loop/mod.rs` — 二进制结果装配
- `src-tauri/src/engine-bridge.ts` → 事件的MessagePack序列化
- `src-tauri/src/engine/tools/agent_comms.rs` — 结构化的代理间消息
- `src-tauri/src/engine/plan/` — 二进制结果聚积
- `Cargo.toml` — 新依赖项: `flatbuffers`, `rmp-serde`（MessagePack）
- `package.json` — 新依赖项: `@msgpack/msgpack`

### Phase 4: Speculative Tool Execution (Branch Prediction for Agents)

**风险：** 中高 - 需要仔细的回滚逻辑
**依赖关系：** 第0 + 1阶段（需要计划DAG和约束解码）

#### 是什么

当模型开始逐个代币生成工具调用时，我们通常可以在完成之前预测完整调用。对于常见模式：

- `google_calendar_list` → 下一个调用可能是 `google_calendar_create` 或 `gmail_send`
- `request_tools("email")` → 下一个调用可能是 `gmail_send`
- `memory_search` → 下一个调用可能 `memory_store` 或使用检索信息的工具调用

推测执行**预热**或甚至**预激活**模型仍在生成时的下一个可能的API调用：

```
模型正在生成："我首先搜索你的日历……"
  → 引擎预测：下一个工具 = google_calendar_list
  → 引擎预先与 Google Calendar API 进行身份验证
  → 引擎预先获取今天的事件（预测）

模型完成：调用 google_calendar_list(date: "2026-03-06")
  → 引擎：已经有了数据！立即返回。
  节省：200-800ms的API延迟
```

#### 为什么重要

经过第0阶段（计划DAGs），许多任务仍然需要2-3个连续推理调用——模型可以看到结果，然后决定下一步。推测执行把*下一个*步骤API延迟隐藏在*当前*步骤推理延迟后面。

这是人工智能代理的等价于**CPU分支预测**。现代CPU会在知道条件分支将以哪种方式执行之前推测性地执行指令。我们同样执行：在模型决定下一步工具调用之前。如果我们正确预测（常见模式的命中率达到70%），用户就会看到即时结果。如果错了，则静默丢弃推测结果。

#### 如何构建

1. **模式数据库** — 分析历史工具调用序列以构建过渡概率矩阵：
   ```
   P(google_calendar_create | google_calendar_list) = 0.45
   P(gmail_send | gmail_search) = 0.62
   P(memory_store | memory_search) = 0.38
   ```

2. **阈值** — 仅当 P(下次工具 | 当前工具) > 0.5 时才推测（可配置）。

3. **只读推测** — 仅推测**读**操作（列表、搜索、获取）。永远不要推测执行写操作（发送、创建、删除）。这样就完全 Eliminates 回滚复杂性。

4. **连接预热** — 即使我们不触发预测调用，也可以预先建立到下一个API端点的TCP/TLS连接。仅此一项每次调用节省100-300ms。

5. **不匹配时取消** — 如果模型调用了与预测不同的工具，则取消预测请求（如果仍在进行中），然后正常进行。

#### 影响

| 场景 | 之前 | 之后 |
|----------|--------|-------|
| 日历列表 → 创建事件 | 400毫秒API延迟 | 0毫秒（预取）|
| 邮件搜索 → 发送邮件 | 300毫秒API延迟 | 100毫秒（连接预热）|
| 内存搜索 → 使用结果 | 50毫秒搜索延迟 | 0毫秒（预搜索）|
| 误预测 | 不适用 | 预测结果被丢弃，无成本 |

**预期命中率：** 在常见工作流程（日历、电子邮件、内存模式）上为60-70%。

#### 受影响的文件
- `src-tauri/src/engine/speculative/` — 新模块（预测器、缓存、执行器）
- `src-tauri/src/engine/agent_loop/mod.rs` — 在工具完成后触发推测
- `src-tauri/src/engine/tools/mod.rs` — 记录工具序列以学习模式
- `src-tauri/src/engine/sessions/schema.rs` — `tool_sequences` 表用于模式存储

## 跨领域：安全性不变量（所有阶段）

这些安全属性适用于每个阶段。它们不是可选的增强功能 — 这些是每个阶段在发布前必须满足的硬性要求。

### 提示中的个人信息和秘密脱敏

当代理相互通信、调用工具或输出执行计划时，它们处理真实用户数据——API密钥、OAuth令牌、电子邮箱地址、电话号码、凭证、财务数据。这些都不应因不必要的原因泄露到模型上下文中。

**脱敏流水线：**

每个流输入提示的数据 —— 工具结果、代理间的通信、Action DAG 输出、内存回想 —— 都要经过脱敏层才能到达LLM:

1. **密钥空白** — 任何匹配已知秘密模式的字符串都会在注入上下文前被替换为`[REDACTED]`：
   - API密钥: `sk-`, `GOCSPX-`, `xoxb-`, `ghp_`, `glpat-`, 等等。(正则表达式模式库)
   - OAuth令牌: `ya29.`，`eyJ`(JWT)，承载式令牌
   - 私钥: `-----BEGIN`，长度超过64字符的十六进制字符串
   - 环境变量: 任何载入`.env`的包含`SECRET`, `KEY`, `TOKEN`, `PASSWORD`的字段

2. **PII识别** — 结构化PII会被识别和屏蔽:
   - 电子邮箱地址 → `j***@example.com`（第一个字符+域名可见）
   - 电话号码 → `+1 ***-***-1234`（最后4位数字可见）
   - 信用卡号 → `****-****-****-5678`
   - 社保号/国家ID → `***-**-6789`
   - 内网IP地址 → 正常通过；公共IP → `***.***.***.***`

3. **按工具脱敏策略** — 有些工具确实需要PII（如`gmail_send`需要收件人邮箱）。脱敏层有针对工具的白名单:
   ```
   gmail_send: 允许在[to, cc, bcc]字段中的[email_address]
   google_api: 允许在[body]字段中的[email_address]
   memory_store: 允许[all] — 用户明确要求记得
   agent_comms: 脱敏[all secrets], 允许[获得用户同意的PII]
   ```

4. **输出时提示清理** — 在模型的响应显示给用户或存储在会话历史之前，生成后扫描捕捉模型可能重复的任何密钥。如果模型重复一个令牌或密钥（即使部分），它在存储/显示的版本中会被替换为`[REDACTED]`。

5. **计划DAG参数净化** — 当模型生成Action DAG（阶段0）时，计划验证器检查每个参数值相对于密钥模式库。如果工具参数包含原始密钥（例如，模型试图传递一个API密钥作为函数参数而不是使用保险库），则会拒绝该计划并提示:"安全：节点'b'中的参数'api_key'包含密钥。请改用保险库引用。"

**我们已有的:** `security.ts` 注入扫描仪（30多种模式）和 `credential_activity_log` 表提供了基础。脱敏流水线从"检测和警告"扩展为"检测并空白，确保模型看不到。"

### 加密代理间通信

当智能体A委托给智能体B——或者当智能体在队列、编排器或立体网格单元中交换消息时——传输中和静止的数据必须加密。这在二进制IPC（第三阶段）中尤其重要，因为在那时人类可读检查不再可能。

**加密架构:**

1. **传输中加密（智能体间）** — 所有智能体间的消息在写入 `agent_messages` 表或通过二进制IPC总线之前都要用AES-256-GCM加密：
   - 加密密钥：从操作系统密钥链中的应用程序主密钥派生（与当下保护凭据的密钥相同）
   - 每条消息都有一个独特的12字节随机数
   - 密文+随机数+标签被存储；明文永远不会接触SQLite
   - 解密仅在内存中进行，在接收智能体的上下文正在建立时

2. **瞬时上下文密钥** — 对于Plan DAG执行（第0阶段）和多维网格单元，生成了一次性执行密钥：
   - 计划执行程序在计划开始时生成一个随机的256位密钥
   - 所有中间结果（工具输出、部分状态）都用此密钥在内存中加密
   - 当计划完成且结果已合成时，暂时密钥被销毁
   - 这意味着若进程在计划中途崩溃，中间结果无法恢复——这是设计使然

3. **内存加密** — 记忆已经用AES-256-GCM加密敏感内存字段。新阶段继承此项：
   - 工具嵌入（第2阶段）：不加密（工具描述不敏感——对所有用户都一样）
   - 推测缓存（第4阶段）：静止时加密，如果有用户数据；对只读查询的推测结果（日历事件、电子邮件主题）在缓存前用主密钥加密

4. **二进制协议加密（第3阶段）** — 当我们转到二进制IPC：
   - 前端与引擎间的MessagePack负载：通过在应用启动时协商的会话特定密钥加密（Tauri IPC已经是进程本地的，但多层防御）
   - 智能体间Protobuf消息: 在序列化层面加密——`encrypt(serialize(message))`，而不是`serialize(encrypt(message))`。这确保二进制格式本身不泄漏结构。

5. **日志中零明文密钥** — 日志记录器（已在`logger.ts` / Rust `tracing`中实现）被扩展了一个脱敏格式化器，从所有日志输出中清除密钥，包括调试和跟踪级别。出现在工具结果、智能体消息或计划参数中的密钥绝不会以纯文本写入磁盘——即使在开发模式下也是如此。

**审计痕迹:** 每次智能体间消息交换都记录在`credential_activity_log`中，包含：时间戳、发送智能体ID、接收智能体ID、操作类型（`delegate`、`broadcast`、`respond`）以及是否应用了加密。消息内容本身并未记录——仅记录元数据。

## 这不是什么

明确说明我们*不*在构建什么:

- **不是"数字心灵感应"** — 模型不会交换原始隐藏状态。没有模型的内部表示与其他模型兼容。这是一个未解决的研究问题，不是一项工程任务。

- **不是"潜在空间传输"** — 词元化器/反词元化器不是瓶颈。这仅需微秒。变换器的前馈通过需要数秒。跳过词元化器会节省0.01%的时钟时间。

- **不是"直接状态注入"** — 我们不允许可信AI绕过我们的安全堆栈修改变量。监管者协程的API级监控、OAuth作用域限制和人工环路批准都保持不变。

- **不是一个新型互联网协议** — Gmail、Slack和GitHub暴露REST API。我们用REST与之对话。在内部, 在我们自己的组件之间，我们进行优化。但假装全世界会重写其架构是不现实的。

*这*是：消除不必要的工作。更少的推理调用。更少的解析失败。更快的内部通信。更智能的工具选择。每项改进都是可测量的、可撤销的，并基于计算机科学常识（DAG、约束语法、向量搜索、二进制序列化、推测执行）。
